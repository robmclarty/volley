## Frame

- **Problem:** volley is about to become the step builder under a scheduler that runs many steps in parallel, and three things stand in the way. Every iteration runs the builder at one effort, so a settled step costs what a hard one does. The builder's first attempt is judged against prose criteria, which a critic can negotiate with and a test cannot. And runciter reaches volley only through a bespoke kind in its own repo that pins volley's version range, reads its `summary.json`, and breaks when volley moves.
- **Smallest thing that solves it:**
  - An **effort ladder**: each build runs the builder one rung further up `--effort-ladder`, capped at the last rung; the critic's effort is its own flag and defaults high once a ladder is set; the rung and why it climbed are in the summary.
  - A **tester seat**: before the first build, a read-mostly seat writes a failing test from the criteria into the test and fixture gate paths; the check must go red; a green check ends the run with no builder spend.
  - A **protocol mode**: `volley run --protocol runciter.run/1` reads runciter's `RunInput` on stdin and writes one `RunOutput` on stdout, so runciter's `process` kind runs volley with no adapter in runciter.
- **Done looks like:** a run with `--effort-ladder low,medium,high` converges on a cheap first iteration when the work is easy and climbs when it is not, and the summary says which; a run with the tester on shows red at iteration 1 and green by the last, or stops early with `tester_passed_early`; `echo <RunInput> | volley run --protocol runciter.run/1` exits 0 with one valid `RunOutput`, and the same command under runciter's `process` kind builds a task on the sandbox repo.
- **Explicitly NOT doing:** the ensemble (`--builders N`), `--critic-prefilter`, `volley optimize`, any new seat beyond the tester, the sandbox extraction, deleting runciter's `volley` kind (runciter's repo, after this lands), lessons on the protocol result beyond the empty list, a run deadline from `budget.timeout_ms` (runciter enforces it), and a rung that means something on a local model (a step cap, say).

## Architecture sketch

```
iteration n
├─ test      iteration 1 only: tester (critic's effort) writes a failing test under the test and fixture gate paths
│            cap crossed? skip the rest · check → red? continue · green? end the run: tester_passed_early
├─ build     builder at ladder[min(builds + 1, len) - 1]
├─ check
├─ critique  critic at --critic-effort (high when a ladder is set, else unset)
└─ record    rung, climbed, tester_changes, tester_cost_usd → iterations/<n>/summary.json

stdin RunInput ── volley run --protocol runciter.run/1 ──┬─ stdout RunOutput (one document)
                  state in <run_dir>/volley/<run_id>/     └─ stderr {"type":"runciter.progress"…}
```

## Decisions

- <a id="d1"></a>**D1 (rung-is-effort)**: A rung sets fascicle's per-call `effort` on the builder's call, never the model, and the ladder takes the five levels `low|medium|high|xhigh|max`, refusing `none`, which on `claude_cli` leaves Claude Code at its own default ([Q14 (none-rung)](#q14)), *because* the seat stays comparable across rungs and effort is the knob every provider exposes or reports ignoring.
- <a id="d2"></a>**D2 (climb-on-failure)**: The rung climbs one step per build that didn't end the run (a failed check or a critic rejection), and the top rung repeats to `max_iterations`: build *k* runs at `ladder[min(k, len) - 1]`, the count rides in `LoopState`, and a resume reads it back from the last iteration's `summary.json` ([Q13 (rung-by-builds)](#q13)), *because* a failed cheap attempt wastes cheap tokens and a top-rung first attempt wastes expensive ones on steps that did not need them.
- <a id="d3"></a>**D3 (critic-effort-apart)**: `--critic-effort` is independent of the ladder; it defaults to `high` when a ladder is set, and otherwise an unset critic effort passes nothing, as today ([Q12 (critic-effort-unset)](#q12)), *because* reading a diff costs far less than writing it, the critic is what makes a cheap builder safe, and a default run's critic must stay the control too.
- <a id="d4"></a>**D4 (ladder-off-by-default)**: With no ladder set, no `effort` is passed and the builder's call options are identical to today's, *because* [C4 (claude-arm-unchanged)](#c4) compares runs across seats, and the default arm must stay the control.
- <a id="d5"></a>**D5 (tester-writes-gate-only)**: The tester writes only the test and fixture gate paths ([D20 (tester-tests-and-fixtures)](#d20)) and has no `bash`, confined by volley's tools on most seats and by permission rules on `claude_cli` ([D19 (tester-claude-permissions)](#d19)), *because* its whole job is the test.
- <a id="d6"></a>**D6 (red-before-green)**: After the tester, the check must fail; a check that passes ends the run as `tester_passed_early` with no builder call ([D17 (tester-first-iteration)](#d17)), *because* a test that passes before the build is vacuous or the work is done, and both are the harness's to report, not the builder's to pay for.
- <a id="d7"></a>**D7 (tester-at-critic-effort)**: The tester runs on the critic's provider and model at the critic's effort, *because* writing the right test is reading work, and the critic seat already exists on every run.
- <a id="d8"></a>**D8 (tester-off-by-default)**: `--tester` defaults to `off` in this build; range 2's stop decides whether it turns on wherever a check exists, *because* the default is a judgment about real tasks and nobody has run it on one yet.
- <a id="d9"></a>**D9 (tester-changes-apart)**: The tester's edits are measured and recorded as `tester_changes`, a git checkpoint lands after the tester when checkpoints are on, and the builder's `gate_edits` exclude paths the tester wrote unless the builder changed them further, judged by the hashes of [D22 (tester-hashes)](#d22), *because* a gate edit is a warning about the builder, and the tester editing the gate is the point.
- <a id="d10"></a>**D10 (own-schema-copy)**: volley carries its own zod schemas for `RunInput` and `RunOutput` in `src/protocol/`, transcribed from runciter's §5.4, with no dependency on runciter, *because* [C11 (exact-pins)](#c11) and a builder should not depend on its host to build; runciter's conformance test is the check that the copies agree.
- <a id="d11"></a>**D11 (protocol-exit-table)**: In protocol mode the exit codes are the protocol's (0 with one `RunOutput`, 1 runner error, 2 contract violation, sorted by [D28 (protocol-errors-as-output)](#d28)), documented in their own README table, and `volley run` without the flag keeps its table unchanged, *because* the protocol defines the exit code's meaning for its host and the plain CLI defines it for a person.
- <a id="d12"></a>**D12 (data-carries-summary)**: `RunOutput.data` is the `RunSummary` whole, `status` maps `success` to `passed` and everything else to `failed` with a `fail_reason` from runciter's vocabulary (step 9's table), `summary` is a status line, then the critic's last feedback, cut to 4000 characters and never empty, `usage` is the run's totals with `cost_source: 'estimated'`, `artifacts` names the critic's last feedback ([D26 (protocol-state-in-run-dir)](#d26)), and `lessons` is empty, *because* the host reads pass, cost and a summary, and keeps the rest verbatim for its drawer.
- <a id="d13"></a>**D13 (protocol-refuses-workspace-flags)**: Protocol mode refuses `--worktree`, `--git`, `--json` and a positional prompt with a contract violation, *because* runciter owns the workspace (its R5) and stdout carries the protocol ([C5 (machine-stdout)](#c5)).
- <a id="d14"></a>**D14 (tester-contained)**: A tester on any provider but `claude_cli` needs containment the way a builder does, the sandbox or `--allow-unsandboxed-builder`; a `claude_cli` builder paired with a local tester can't be contained, so that pairing needs the opt-out and config refuses it otherwise; C2 is read as covering both seats, *because* the check executes what the tester writes, so a local tester's test is model-written code running wherever volley runs (reopened by [Q8 (tester-check-executes)](#q8), replacing the no-sandbox answer to [Q1 (tester-containment)](#q1)).
- <a id="d15"></a>**D15 (tester-model-override)**: The tester borrows the critic's provider, model and URL, and `--tester-model` (config `tester_model`, `VOLLEY_TESTER_MODEL`) is its one override, *because* one flag is enough until a real run shows a reason to split the seats (resolves [Q3 (tester-seat-defaults)](#q3)).
- <a id="d16"></a>**D16 (claude-effort-env)**: fascicle's `claude_cli` adapter passes `effort` to the child as `CLAUDE_CODE_EFFORT_LEVEL` (0.17.7, `effort_env_for_claude_cli`), so the claude arm sets `effort` like every other seat and needs no `extra_args`; with no ladder the field is absent and no variable is set, *because* the transport already exists and [D4 (ladder-off-by-default)](#d4) holds without a special case (overtakes the fallback [Q4 (claude-effort-transport)](#q4) settled on).
- <a id="d17"></a>**D17 (tester-first-iteration)**: The tester runs in iteration 1 only, and a green check after it ends the run with the status `tester_passed_early` on exit 2, whose README row gains it; later iterations build against the critic's feedback and the test already in place, *because* iteration 1's test stays in the workspace, so a tester in iteration 2 would find the check green and end the iteration before the builder could act on the critic (resolves [Q5 (tester-first-iteration)](#q5)).
- <a id="d18"></a>**D18 (tester-needs-check)**: `--tester on` with no check, whether `--check none` or a `--check auto` that finds nothing, is a config error naming `--check`, *because* an open gate makes every test pass early, and P1 stops a run that can't succeed before it spends (resolves [Q6 (tester-no-check)](#q6)).
- <a id="d19"></a>**D19 (tester-claude-permissions)**: A tester on `claude_cli` gets its own permission list in `src/claude_cli_permissions.ts`: `Read(/**)`, one `Edit(<glob>)` per writable gate pattern, `Edit` denials for the files [D20 (tester-tests-and-fixtures)](#d20) excludes, and Bash disallowed; under `volley acp` a `claude_cli` tester is refused, as the builder is, *because* a Claude seat never gets volley's tools and its writes skip Zed's prompts (resolves [Q7 (tester-on-claude-cli)](#q7)).
- <a id="d20"></a>**D20 (tester-tests-and-fixtures)**: A tester write must match a gate pattern and must not be `package.json`, a `*.config.*` file, or a path under `.github/`, and a refused path is named in the tool's error, *because* a tester that can rewrite the check's config can make its own result red or green (resolves [Q9 (tester-writable-set)](#q9)).
- <a id="d21"></a>**D21 (tester-cost-apart)**: The tester's spend is `tester_cost_usd`, beside the builder's and the critic's in the state, the iteration archive and the summary, and a branch after the test phase skips build, check and critic when the cap is crossed, as `verify` does after the build, *because* keyframes D6 checks the cap after every phase and each seat's cost is read apart (resolves [Q10 (tester-cost-cap)](#q10)).
- <a id="d22"></a>**D22 (tester-hashes)**: Each file the tester wrote is hashed right after the test phase, and the hashes ride in the state and the archive, where a resume reads them back; after a build, a tester path counts as a builder gate edit only when its hash has changed, *because* changes are measured from the run's baseline and a checkpoint may not exist (resolves [Q11 (tester-changes-baseline)](#q11)).
- <a id="d23"></a>**D23 (ladder-flat-on-local)**: A ladder on a builder whose provider ignores effort (`ollama`, `lmstudio`) warns at config time, each iteration records `effort_ignored`, and the README says the ladder is flat there, *because* fascicle drops effort on those transports, and P4 is met by saying so rather than by inventing a local rung (resolves [Q15 (ladder-on-local)](#q15)).
- <a id="d24"></a>**D24 (protocol-prompt-from-context)**: In protocol mode the prompt is `agent.prompt` followed by the text of `context.md`, and the criteria are `task.criteria`, as runciter's `volley` kind builds them, *because* `context.md` carries the task and its feedback, so a retried task sees why the last attempt failed (resolves [Q16 (protocol-prompt-source)](#q16)).
- <a id="d25"></a>**D25 (protocol-check-from-verify)**: In protocol mode `--check` comes from `stage.verify` as the kind maps it: `none` and a command pass through, and `auto` becomes `pnpm check` when `package.json` has a check script, else `none`; a `--check` in the agent's argv wins, *because* volley should converge on the gate runciter verifies with (resolves [Q17 (protocol-check)](#q17)).
- <a id="d26"></a>**D26 (protocol-state-in-run-dir)**: Unless the argv sets them, protocol mode keeps its state under `<run_dir>/volley` with `run_id` as the run id, and copies the critic's last `feedback.md` to `<run_dir>/artifacts/critic-feedback.md`, named in `RunOutput.artifacts`, *because* runciter owns the workspace, and its diff and verify would see a `.volley/` there (resolves [Q18 (protocol-state-dir)](#q18)).
- <a id="d27"></a>**D27 (protocol-flag-only)**: Only `--protocol runciter.run/1` switches volley into protocol mode, and `RUNCITER_PROTOCOL` in the environment is ignored, *because* runciter sets the variable for every process under a run, the check's own `volley run` tests included (resolves [Q19 (protocol-flag-only)](#q19)).
- <a id="d28"></a>**D28 (protocol-errors-as-output)**: A builder, check or critic error in protocol mode exits 0 with a failed `RunOutput` whose `fail_reason` is `builder_error`, `check_error` or `critic_error`; exit 1 is only for a failure that leaves no `RunOutput` to write, and exit 2 for a config error or bad input, *because* a `RunOutput` keeps the summary and `data` in the drawer, as today's kind does for volley's exits 3, 4 and 6 (resolves [Q20 (protocol-error-exit)](#q20)).
- <a id="d29"></a>**D29 (resume-keeps-ladder)**: A run's `config.json` records `effort_ladder` and `critic_effort`, and `load_resume_state` reads both back, so a resumed laddered run keeps its ladder and its critic's effort with no env var set, and the rung follows on from the archived `builds` ([D2 (climb-on-failure)](#d2)), *because* D2 promises a resume picks up the rung, and a resume that silently drops the ladder sends no effort at all (harvested from range 1's P1).

## Constraints

The repo's `keyframes.md` holds these; they are repeated here by their slugs so each step is checked against them.

- <a id="c1"></a>**C1 (read-only-critic)**: The critic never writes; the tester is a seat of its own, not a critic that writes.
- <a id="c2"></a>**C2 (contained-builder)**: A builder other than `claude_cli` runs only in the sandbox unless opted out, and so does a tester on any provider but `claude_cli` ([D14 (tester-contained)](#d14)); nothing here loosens it.
- <a id="c4"></a>**C4 (claude-arm-unchanged)**: The `claude_cli` builder arm is byte-for-byte unchanged when no ladder is set; the existing test asserts it and a new case asserts the options with and without a ladder.
- <a id="c5"></a>**C5 (machine-stdout)**: stdout carries machine output only; in protocol mode that is exactly one `RunOutput`.
- <a id="c6"></a>**C6 (stable-exit-codes)**: `volley run`'s README exit table keeps every meaning, and exit 2's row gains `tester_passed_early` ([D17 (tester-first-iteration)](#d17)); protocol mode's table is separate ([D11 (protocol-exit-table)](#d11)).
- <a id="c9"></a>**C9 (flow-owns-iteration)**: The tester is a step in the flow's topology; no hand-written loop in `flow.ts`, `phases.ts` or `orchestrator.ts`.
- <a id="c10"></a>**C10 (house-style)**: No classes, named exports, `.js` extensions, no deep sibling imports.
- <a id="c11"></a>**C11 (exact-pins)**: No new runtime dependency; zod is already present.
- <a id="c12"></a>**C12 (check-green-per-step)**: `pnpm check` is green at every checkpoint, the README changes with the behaviour it describes, and `keyframes check` passes.
